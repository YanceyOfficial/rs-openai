# Evals: Runs + Output Items — Design

Status: Approved
Date: 2026-08-20

## Context

Closes Evals' deferred Runs sub-resource — originally deferred because "the run's own request/response shape stayed genuinely unconfirmed after several research attempts." The `gh api` SDK-source technique (now the standing fallback for any `developers.openai.com` gap this session) fully resolves it: `types/evals/run_*.py` gives a complete, generated type set.

**A confirmed reason the shape looked hard before, now precisely understood**: `RunCreateParams.data_source`/`RunCreateResponse.data_source` is a 3-variant union (JSONL / Completions / a `responses` variant) where the `responses` variant alone expands into ~20 further nested named sub-types (a `source` sub-union of file-content/file-id/live-responses-query, an `input_messages` sub-union of template/item-reference with its own nested chat-message/eval-item/content-block unions, sampling params, etc.). This is the deepest single-field type nesting found anywhere in this whole project. Per this crate's established and repeatedly-validated pattern (Audit Log details flattened to a map, `EvalGraderMessage.content` kept raw, `file_search`'s `filters` kept raw), `data_source` is modeled as raw `serde_json::Value` on both request and response sides — not hand-modeled. Everything else in Runs and Output Items is confirmed simple enough to fully type.

**A confirmed shared-shape reuse**: `RunCreateResponse`/`RunRetrieveResponse`/`RunListResponse`/`RunCancelResponse` are structurally identical (same envelope: `id`, `created_at`, `data_source`, `error`, `eval_id`, `metadata`, `model`, `name`, `object`, `per_model_usage`, `per_testing_criteria_results`, `report_url`, `result_counts`, `status`) — modeled as ONE shared `EvalRun` type, matching this crate's established "one struct for genuinely identical create/retrieve/list responses" convention. `RunDeleteResponse` is genuinely different (`deleted`/`object`/`run_id` — **`run_id`, not `id`**, confirmed asymmetry) and stays its own type.

## Goals

### Runs (`apis::evals::runs`, `/evals/{eval_id}/runs`)

- `EvalRuns::create()` (`POST .../runs`), `::list()` (`GET .../runs`), `EvalRun::retrieve()` (`GET .../runs/{run_id}`), `::delete()` (`DELETE .../runs/{run_id}`), `::cancel()` (`POST .../runs/{run_id}`, confirmed via source: cancel is a POST to the same URL as retrieve, no `/cancel` suffix).
- `CreateEvalRunRequest`: `data_source: serde_json::Value` (required), `metadata: Option<serde_json::Value>`, `name: Option<String>`.
- `EvalApiError`: `code: String`, `message: String`.
- `EvalRunPerModelUsage`: `cached_tokens: i64`, `completion_tokens: i64`, `invocation_count: i64`, `#[serde(rename = "model_name")] run_model_name: String` (confirmed field-alias in source), `prompt_tokens: i64`, `total_tokens: i64`.
- `EvalRunPerTestingCriteriaResult`: `failed: i64`, `passed: i64`, `testing_criteria: String`.
- `EvalRunResultCounts`: `errored: i64`, `failed: i64`, `passed: i64`, `total: i64`.
- `EvalRun` (shared response for create/retrieve/list/cancel): `id: String`, `created_at: i64`, `data_source: serde_json::Value`, `error: EvalApiError`, `eval_id: String`, `metadata: Option<serde_json::Value>`, `model: String`, `name: String`, `object: String`, `per_model_usage: Vec<EvalRunPerModelUsage>`, `per_testing_criteria_results: Vec<EvalRunPerTestingCriteriaResult>`, `report_url: String`, `result_counts: EvalRunResultCounts`, `status: String`.
- `ListEvalRunsRequest`: `after: Option<String>`, `limit: Option<u32>`, `order: Option<SortOrder>`, `status: Option<String>` (`"queued"`/`"in_progress"`/`"completed"`/`"canceled"`/`"failed"`, plain string).
- `ListEvalRunsResponse`: universal list shape, `data: Vec<EvalRun>`.
- `DeleteEvalRunResponse`: `deleted: Option<bool>`, `object: Option<String>`, `run_id: Option<String>` (all confirmed `Optional` in source — kept as such, not defensively widened).

### Output Items (`apis::evals::runs::output_items` — colocated in the same file)

- `EvalRunOutputItems::list()` (`GET /evals/{eval_id}/runs/{run_id}/output_items`), `EvalRunOutputItem::retrieve()` (`GET .../output_items/{output_item_id}`). No create/update/delete — confirmed, output items are generated by the run, not user-managed.
- `EvalRunOutputItemResult`: `name: String`, `passed: bool`, `score: f64`, `sample: Option<serde_json::Value>`, `kind: Option<String>` (`#[serde(rename = "type")]`), plus `#[serde(flatten)] extra: HashMap<String, serde_json::Value>` (confirmed: the source's `Result` type has an explicit arbitrary-extra-properties escape hatch for grader-specific fields — modeled the same way Audit Logs' per-event detail was).
- `EvalRunOutputItemSampleInput`: `content: String`, `role: String`.
- `EvalRunOutputItemSampleOutput`: `content: Option<String>`, `role: Option<String>`.
- `EvalRunOutputItemSampleUsage`: `cached_tokens: i64`, `completion_tokens: i64`, `prompt_tokens: i64`, `total_tokens: i64`.
- `EvalRunOutputItemSample`: `error: EvalApiError`, `finish_reason: String`, `input: Vec<EvalRunOutputItemSampleInput>`, `max_completion_tokens: i64`, `model: String`, `output: Vec<EvalRunOutputItemSampleOutput>`, `seed: i64`, `temperature: f64`, `top_p: f64`, `usage: EvalRunOutputItemSampleUsage`.
- `EvalRunOutputItem` (shared for retrieve/list — confirmed identical shape): `id: String`, `created_at: i64`, `datasource_item: serde_json::Value` (arbitrary, matches every other "data source item" field in Evals staying raw), `datasource_item_id: i64`, `eval_id: String`, `object: String`, `results: Vec<EvalRunOutputItemResult>`, `run_id: String`, `sample: EvalRunOutputItemSample`, `status: String`.
- `ListEvalRunOutputItemsRequest`: `after: Option<String>`, `limit: Option<u32>`, `order: Option<SortOrder>`, `status: Option<String>` (`"fail"`/`"pass"`).
- `ListEvalRunOutputItemsResponse`: universal list shape, `data: Vec<EvalRunOutputItem>`.

## Non-goals

None beyond `data_source`'s deep nesting, already scoped above.

## Design notes

- File organization: new `interfaces/evals/runs.rs` and `apis/evals/runs.rs` (Evals is currently a flat single-file module — this is the first sub-resource split it gets, matching how other multi-resource categories are organized as directories once they grow a real sub-resource).
- No `client.rs` changes.
- `apis::evals` continues the crate's no-glob-re-export convention for this new submodule.
- `cancel()`'s route is confirmed to be the SAME URL as `retrieve()`/an implicit delete-adjacent path — `POST /evals/{eval_id}/runs/{run_id}`, not a `/cancel` suffix. Verify this doesn't collide with any hypothetical `update` (there is none — Runs has no update method, confirmed).

## Testing

`wiremock` tests: Runs (5: create with `data_source` round-tripping through raw JSON/retrieve/list/delete asserting `run_id` not `id`/cancel), Output Items (2: list/retrieve, including a test proving `EvalRunOutputItemResult`'s `#[serde(flatten)]` correctly captures an unmodeled grader-specific field).

## Versioning

Purely additive, no `client.rs` changes. Closes Evals' last deferred piece.
